Normalization Confluence

When can repair replace commutativity?

Normalization confluence gives an exact theory of when repair can replace raw commutativity: concurrent systems whose events may conflict and break invariants, and whose replicas still converge because a deterministic repair restores them.

Dayna Blackwell, Blackwell Systems. Every result machine-checked in Coq.

Same events, different results

Replicas apply the same events in different orders, because networks delay, reorder and retry messages. After each event, every replica runs the same repair to restore its invariants. Do replicas that have seen the same events end in the same state?

Not always. A shelf holds 5 items and has 4 in stock. Two events arrive, "add 3" and "remove 1", and repair caps the stock at 5.

Replica A applies "add 3" (7), repairs (5), then "remove 1": 4. Replica B applies "remove 1" (3), then "add 3" (6), repairs: 5.

Same events, same repair, different stock.

The theory says which condition fails. Take the raw state 7, just after "add 3". Repairing first and then removing 1 gives 4. Removing 1 from the raw 7 and then repairing gives 5. The one-event condition below, state descent, requires these two to agree, so this shelf cannot converge in every order. gsm finds a diverging order at build time.

Three conditions

Raw states may differ along the way; what has to agree is the result after repair. Write N for the repair. The theory proves an exact condition at three scales:

One event

State descent

Applying an event to a state or to its repaired form gives the same result after repair: N(e(N x)) = N(e x). Convergence requires it.

DescendsOn
A sequence of events

History descent

Every reordering the delivery model allows gives the same result after repair: free, causal, at-least-once, or declared independence.

history_from_descent · local_exact
An infinite run

Canonical recurrence

On networks where repair may never stop, every fair run eventually stays on one repaired result.

C1_closed · canon_settles_quotient_invariant

  • descent_not_history: state descent without history descent. Repair does nothing, and two events that do not commute separate a reordering.
  • history_not_descent: history descent without state descent. One event, so every reordering is trivial, while the event does not respect what repair identifies.
  • history_from_descent: given state descent, history descent of the raw runs is the same question about the repaired runs.
  • nd_derived_from: with terminating repair, every run from a start has one result exactly when history descent and state descent both hold there.

Every condition is exact: necessary and sufficient, with a counterexample for each hypothesis. Repair strictly enlarges what can converge. CRDTs are the case where repair never runs, and some systems converge only because of their repair, which no CRDT on the same operations can match.

Three layers

The same structure organizes the results across regimes. Three layers, and three proved interfaces between them:

Layer A

Execution

Which executions count as the same. One theorem recovers the exact results for causal, at-least-once and declared-independence delivery, and for reconfiguration.

local_exact · closure_exact
Layer B

Consistent states

The fixed points of repair are exactly the solutions of a constraint problem, which places consistency in known constraint-satisfaction algebra.

section_iff_csp · pol_gamma_iff
Layer C

Long-run behavior

Whether runs settle, and where. Oscillation, livelock and settling on the wrong state are classified in one vocabulary.

C1_closed
  • A to B: an event must respect consistency only after repair, not strictly. Strict commutation is sufficient but not needed, and a real federation shows the difference. xu_iff_respects · strict_not_necessary
  • B to C: a system can have exactly one consistent state and still never reach it. flip2_unique_solution_livelock · settled_canon_exact
  • A to C: local conditions plus termination give convergence (Newman's lemma), and fair schedules alone do not, exactly when some action is starved forever. newman_bridge · four_point_fair_not_confluent · fair_sn_exact
  • Normalization confluence is the base case. The single-registry theorem is derived from the framework's kernels, unchanged: the one-event condition is state descent and the commutation condition is history descent. The framework was built after that theorem, so this is a derivation, not a prediction. nd_derived_from · nd_cc_exact

Tests on outside theorems

Recovering results the framework was built from shows organization, not reach. So the test is stricter: freeze every existing proof file, fix the pass criterion in advance, and recover a classical theorem from outside the repository. Whatever the frozen framework cannot express is reported as a leak.

Passed

Dijkstra's self-stabilization (1974)

A finite system stabilizes under fair schedules exactly when no fair loop leaves the legitimate states: one line from layer C. Dijkstra's K-state token ring follows for every ring size with K at least the number of machines, under fair and arbitrary schedules. Three leaks, all stated.

Checking a system with gsm

gsm checks these conditions at build time: a team declares its business rules and repairs, and the build verifies that concurrent updates converge to one valid state, or names the order that diverges. It also checks a rules change before deployment, under the delivery the system actually has. Here is the shelf:

r := gsm.NewRegistry("shelf")
stock := r.Int("stock", 0, 8)

r.Invariant("fits_on_shelf").
    Watches(stock).
    Holds(func(s gsm.State) bool { return s.GetInt(stock) <= 5 }).
    Repair(func(s gsm.State) gsm.State { return s.SetInt(stock, 5) }).
    Add()

r.Event("add_3").Writes(stock).
    Apply(func(s gsm.State) gsm.State { return s.SetInt(stock, min(s.GetInt(stock)+3, 8)) }).Add()
r.Event("remove_1").Writes(stock).
    Apply(func(s gsm.State) gsm.State { return s.SetInt(stock, max(s.GetInt(stock)-1, 0)) }).Add()

_, report, err := r.Build()
err: gsm: Compensation Commutativity (CC) check failed
  WFC: PASS (max repair depth: 1)
  CC (Compensation Commutativity): FAIL
    Events: (add_3, remove_1)
    State:  {stock=0}
    add_3→remove_1: {stock=2}
    remove_1→add_3: {stock=3}

The build refuses the machine. The first divergence it reports is on an empty shelf, where removing first does nothing: "add 3" then "remove 1" gives 2, the other order gives 3. Output from gsm v0.16.0, abridged.
