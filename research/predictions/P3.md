# P3: CouchDB and PouchDB resurrect a deleted document on computed delivery orders

Committed on 2026-10-11, before CouchDB or PouchDB was run on any of the orders below. The commit
that adds this file is its timestamp. The setting, the claims, the criteria and the probability
are not edited after this commit. The framework kernels are frozen ([README.md](README.md)).

P2 was a bet on which side of a proved distinction a new system falls. P3 is of a different kind:
the framework's exact theorems and a model of real code compute an answer, and the running
software is the experiment. The mathematics is not in doubt; the risk is whether the model
matches the software.

## Setting

- **Document.** One document with a linear history of four revisions, `1-a`, `2-b`, `3-c`, `4-d`,
  where `4-d` is a deletion. Revision ids are 32 hex characters (`aaaa...`, `bbbb...`, `cccc...`,
  `dddd...`).
- **Delivery.** Each revision is delivered once, with its full revision history (the path from
  `1-a` to itself), in each of the 24 orders, to a fresh document id with `revs_limit` 3.
  - CouchDB 3.5.3 (official image, single node, `q=1`, `n=1`): one `POST /db/_bulk_docs` with
    `new_edits: false` per revision, each waiting for its response.
  - PouchDB 9.0.0 (Node): one `bulkDocs` call with `new_edits: false` per revision, each awaited.
- **Configurations.** (i) CouchDB with default settings; (ii) CouchDB with
  `[couchdb] stem_interactive_updates = false`, every order delivered, then the database compacted
  once and read after compaction finishes; (iii) PouchDB with default settings.
- **Observation.** After the four deliveries: whether the document is live (`GET /db/id` returns
  it) or deleted, and for a live document its winning revision.
- **The computed table.** [route2/predictions_S1.json](route2/predictions_S1.json), generated by
  [route2/export_predictions.py](route2/export_predictions.py) from the models
  [route2/couch_model.py](route2/couch_model.py) and [route2/pouch_model.py](route2/pouch_model.py),
  transcribed from `couch_key_tree.erl` and `couch_db_updater.erl` (CouchDB 3.5.3) and
  `pouchdb-merge` (PouchDB 9.0.0). The harnesses are [route2/couch_harness.py](route2/couch_harness.py)
  and [route2/pouch_harness.js](route2/pouch_harness.js).

## Claims (each scored separately)

1. **CouchDB, default settings:** the document ends live, with winning revision `1-a`, on exactly
   the 6 orders in which `1-a` is delivered last, and deleted on the other 18.
2. **CouchDB, `stem_interactive_updates = false` then compaction:** the document ends deleted on all
   24 orders.
3. **PouchDB, default settings:** the document ends live on exactly the 12 orders in which `1-a` is
   delivered after `4-d`, and deleted on the other 12.

In plain words: whether a deleted document comes back depends only on the order in which the same
four revisions arrive; CouchDB's per-update pruning setting changes the outcome; and two
implementations of the same algorithm disagree.

## What the framework contributes, stated as it is

- The at-least-once exact theorem (`alo_exact`: convergence under every order and duplication iff
  commutation at reachable states and idempotence) says what decides convergence. gsm, run on the
  model's registry, reports the failing pair (`1-a`, `2-b`, after `4-d`) and that duplicate
  delivery is not the cause (output in [route2/gsm_couch.out](route2/gsm_couch.out)).
- State descent explains claim 2: pruning after every update breaks it, pruning once at the end
  (compaction) does not.
- The exact orders in claims 1 and 3 are computed by running the models over all 24 orders, not by
  a theorem.

## Prior art (checked before commitment; nothing was run)

The resurrection itself is known and treated as an accepted tradeoff: COUCHDB-1649 (2013,
`revs_limit` 3, through a history gap), COUCHDB-988 (2010: stemming conflicts are "generally
considered an acceptable tradeoff"), PouchDB #8311 and #9085, and a maintainer comment on
apache/couchdb#4034 (2022). The repair that joins mergeable branches comes from COUCHDB-1163
(2011); merge order inside one batch is discussed in the apache/couchdb PR 958 review (2017).
`stem_interactive_updates` is documented only as a performance switch (2.2 release notes; PR 958:
"an optimization not a behavior change"). Not found in any source: the dependence on delivery order
with full histories, the rule for which orders resurrect, the healing of a stray `1-a` by a later
`2-b` or `3-c`, the flag changing the outcome, and any CouchDB and PouchDB difference. Details in
[route2-survey.md](route2-survey.md#prior-art-found-after-the-survey). The claimed novelty is those
parts only; the resurrection is not presented as a bug.

## Pass and fail

- **Repetitions.** Each order is run three times, each time in a fresh database. If the three runs
  of an order disagree, that order is reported as nondeterministic and excluded from scoring, with
  the count of excluded orders stated.
- **Pass (per claim):** every scored order matches the computed table.
- **Fail (per claim):** any scored order that does not match, reproduced in all three runs.
- **Overall:** P3 passes if all three claims pass. If some claims pass and some fail, the outcome is
  recorded per claim.
- **Out of scope:** the larger scenarios in the survey (S2, S3), duplicate delivery, and the
  replicator itself. They may be run and reported, but they are not scored.

## Probability

About 0.75 that all three claims hold: the models are transcribed from current code
(`couch_key_tree.erl` is unchanged between 3.5.3 and main), the path is sequential and
deterministic, and the main risks are a transcription error in the merge or repair code, or a
detail of `_bulk_docs` or `bulkDocs` the model does not capture.
