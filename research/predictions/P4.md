# P4: A stale tombstone splits a Sync Gateway pushAndPull replication

Committed on 2026-10-13, before Sync Gateway was run on any of the steps below. The commit that adds
this file is its timestamp. The setting, the claims, the criteria and the probability are not edited
after this commit. The framework kernels are frozen ([README.md](README.md)).

Like P3, P4 is a computed prediction: a model transcribed from the real code says what the running
software will do, and the running software is the experiment. Unlike P3, the predicted behavior is a
divergence that would contradict the vendor's documentation, and no record of it was found before
commitment.

## Setting

- **Software.** Couchbase Sync Gateway 4.1.2 (the latest 4.x release; the modeled logic is unchanged
  on `main` at `f1c59eb2`), Community or Enterprise Edition, each gateway on its own Couchbase Server
  bucket. Record the exact Sync Gateway version and Couchbase Server build.
- **Topology.** Two gateways, A and B, with different source ids. A runs one Inter-Sync Gateway
  Replication to B: `{"direction": "pushAndPull", "continuous": true, "conflict_resolution_type":
  "default"}`. B has no replication configured and is the passive peer. Default `max_concurrent_revs`;
  delta sync off.
- **Sync function on A** (B uses the default):
  `function(doc, oldDoc) { if (doc._deleted && doc._rev.indexOf("2-") == 0) { var t = Date.now(); while (Date.now() - t < 8000) {} } channel("*"); }`
  It delays only the write of the first tombstone (revision generation 2) on A, so that the second
  tombstone commits first. `javascript_timeout` is left at its default (none).
- **Steps** (one fresh document id `x` per run):
  1. Create `x` on A; wait until both gateways hold `1-` of `x`.
  2. On B: `DELETE x` (tb1, revision `2-`).
  3. Wait 1 s (A is inside the delayed sync function, so B has already sent tb1).
  4. On B: `PUT x {"v": 2}` (re-create, `3-`), then `DELETE x` (tb2, `4-`).
  5. Wait 10 s. Read A's `GET /{keyspace}/_raw/x` (the regression check, claim 1).
  6. On A: `PUT x {"v": 4}` without `_rev` (a4).
  7. Wait until the replication is idle: 60 s with no change in its push and pull counters.
  8. Read `x` on both gateways, and A's replication status and stats.
- **Observation.** Whether `x` is live or deleted on each gateway, its body, A's `_vv` (current
  version and previous versions), and the replication's conflict counters.
- **The model and its result.** [p4/sg_model.py](p4/sg_model.py) transcribes the code paths listed in
  [p4/REPORT.md](p4/REPORT.md) (sections 1 and 2); [p4/search.py](p4/search.py) explores every
  interleaving; [p4/trace_p8.py](p4/trace_p8.py) replays the predicted order and its controls
  ([p4/results/](p4/results/)). An adversarial review of every link against the Go source is in
  [p4/REVIEW.md](p4/REVIEW.md).

## Claims (each scored separately)

1. **Regression.** After step 5, A holds `x` deleted, its revision-tree winner is the `4-` tombstone,
   and its `_vv` current version is B's source at tb1's value, with no entry for B's source at or
   above tb2's value.
2. **Divergence.** After step 7, `x` is live with `{"v": 4}` on A and deleted on B, and the
   replication is idle with nothing pending.
3. **Control.** The same steps with the sync-function delay removed end with `x` live with
   `{"v": 4}` on both gateways.

In plain words: in the recommended setup, two deletions of the same document that reach the active
gateway out of order make it forget the newer one; its next write is then rejected by the passive
gateway and never retried, and the two clusters stay different for good.

## What the framework contributes, stated as it is

- The frozen single-registry characterization (`nd_derived_from`, `NormalizationDerived.v`): a
  registry has a unique outcome for every buffer exactly when the repaired steps agree on every
  permutation and every event descends at the reachable states. The model shows that the two
  tombstone deliveries do not commute at a state that is reachable because Sync Gateway separates
  its dominance check (when the change arrives) from its merge (when the revision is written), and
  the tombstone-on-tombstone path does not repeat the check. By that theorem the outcome then depends
  on the order.
- The search was guided by the distinction between repair that runs with the event and repair that
  runs separately (`AtomicRepair.v`, written after the freeze; not a kernel and not used in the
  argument above).
- The specific trace, the outcomes and the topology are computed by running the model, not by a
  theorem.

## Prior art (checked before commitment; nothing was run)

- The tombstone-on-tombstone path comes from CBG-1044, "Don't trigger conflict resolution for two
  tombstones" (2020, rev-tree era, where the rev-tree winner made it harmless); it was carried into the
  version-vector path.
- Related but different: CBG-1127 (resurrected tombstones without shared history), CBG-4894 (the
  default resolver prefers a tombstone; deliberate, not described in the 4.x docs), CBG-5853 / PR #8884
  (tombstone bodies failing body validation).
- GitHub issues and pull requests of couchbase/sync_gateway: nothing matching. Couchbase JIRA: no
  public ticket about a current version moving backwards, out-of-order revisions of one document, or a
  conflict rejection blocking a pushAndPull replication. Most 4.x tickets are not publicly visible, so
  an internal ticket cannot be ruled out.
- Documentation (docs-sync-gateway, release/4.0 and release/4.1): conflicts are resolved during pull
  and a pushAndPull replication is recommended when conflicts occur; "Deterministic conflict
  resolution across all clusters". No exception for tombstones. Claim 2 would contradict the
  implied guarantee that a pushAndPull replication with the default resolver converges.

## Pass and fail

- **Repetitions.** Five runs of the delayed configuration (claims 1 and 2) and five of the control
  (claim 3), each on a fresh document id.
- **Pass (per claim):** at least 4 of 5 runs show the claimed state.
- **Fail (per claim):** no run shows it.
- **Reached, not forced:** 1 to 3 runs show it; reported as such, neither pass nor fail.
- **Overall:** P4 passes if claims 1 and 2 pass and the control passes. If the control fails, the
  delayed runs are not scored as a pass, because the setup itself would then be in doubt.
- **Out of scope:** the race without the forced delay, topologies where both gateways pull, push-only
  replication (documented), and the tombstone-preference documentation gap. They may be run and
  reported, but they are not scored.

## Probability

About 0.6 that claims 1 and 2 pass as written. The model's author estimated 0.45 and the
adversarial reviewer about 0.75 for claim 1 and 0.65 to 0.7 for claim 2. The main risks: the delayed
sync function does not keep tb1's write open across tb2's commit; B does not send tb1 while it is
still current (it would then send no revision); tombstone bodies fail body validation on A (CBG-5853);
or a guard in the revision tree that neither reading found.

## If it passes

The finding would be reported to Couchbase as a bug report with the reproduction, following their
contribution rules, after the outcome is recorded here.
